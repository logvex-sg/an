# Universal Compatibility

LOGVEX CRYSTAL targets a wide Minecraft range from one shared core plus a small set of per-band
compatibility adapters. This document describes the adapter architecture, the version registry that
drives it, and the guard that keeps version-specific code out of the shared core.

## The compatibility problem

Between 1.21.1 and the 26.x line, Mojang renamed types that a rendering or event call site has to
name directly. A few of these cannot be papered over with a call that exists on both sides, because
the types themselves changed:

| Band | Minecraft | Why it needs its own adapter |
| --- | --- | --- |
| `pre-matrix` | 1.21.1 – 1.21.5 | `MatrixStack` + `HudRenderCallback` + legacy world events |
| `pre-world` | 1.21.6 – 1.21.8 | `Matrix3x2fStack` + `v1.hud`; still legacy world events |
| `no-world-event` | 1.21.9 | as `pre-world`, but no world render event exists at all |
| `pre-layers` | 1.21.10 | + typed `v1.world` context; old layer/sound factories |
| `modern` | 1.21.11+ | `RenderLayers` factories + `lineWidth` + `ui()` sound |
| `mojang` | 26.x | deobfuscated Mojang namespace; adapter pending |

Only one band is ever on the compile path. `build.gradle` picks it from the selected Minecraft
version and adds `src/versioned/<band>/java` to the main source set, so the unused implementations
cannot leak into a build.

## Adapter architecture

Shared code never names a version-specific type. It calls a band-agnostic route on the
`com.logvex.crystal.compat.Compat` facade; each band provides its own implementation of that route
in `src/versioned/<band>/java/com/logvex/crystal/compat/CompatHooks.java`.

Current routes:

| Route | Purpose |
| --- | --- |
| `matrixPush` | Begin a matrix for custom drawing, whichever stack type the band uses. |
| `worldMatrices` | Obtain the world render matrices in the band's shape. |
| `splashText` | Read the main-menu splash text, which moved between versions. |
| `drawTexture` | Draw a GUI texture, whose signature changed three times across the range. |

Each route is documented at its declaration in `Compat.java`, and each hook fails safe: when a
capability is unavailable in a band, the route degrades to a no-op rather than throwing.

### Why not reflection

Reflection is not the default strategy. It hides real breakage behind a runtime failure and makes
the compatibility surface invisible to the compiler and to static checks. Reflection is only
justified where a band genuinely cannot name the type at compile time, which is not the case for any
current route. New routes should prefer a band-specific implementation over a reflective lookup.

## Version registry

`build-system/version-registry.json` is generated by `build-system/version_registry.py` from two
sources of truth — the generated version inventory (`build-system/versions.json`) and the
compatibility manifest (`build-system/compatibility-manifest.json`). It records, per version:

- Minecraft version and version family.
- Support status: `supported`, `experimental`, `blocked`, or `unsupported`.
- Fabric support, loader requirement, Fabric API coordinate.
- Java runtime requirement, mappings, Loom plugin.
- Adapter identifier (the compat band).
- Build status, test status, release status.

The registry never invents requirements: every field is derived from upstream metadata. A version is
not advertised as supported merely because its metadata allows it to load — the support status is
set from what the adapter layer and certification actually cover.

Regenerate and check it:

```bash
python3 build-system/version_registry.py
python3 build-system/version_registry.py --check   # fails if the JSON is stale
./gradlew checkVersionRegistry
```

## Adapter-leak guard

`build-system/check_adapter_leaks.py` scans the shared source roots for imports or references to
symbols that are only valid in some bands. The forbidden-symbol list lives in
`build-system/adapter-guard.json`, driven from `breaking-changes.json`, so the rule set is reviewable
and data-driven rather than hard-coded in the script.

```bash
python3 build-system/check_adapter_leaks.py
./gradlew adapterGuard
```

The same rule runs as a JUnit test (`AdapterLeakGuardTest`) so `./gradlew test` enforces it too. When
the guard fires, the fix is to route the call through the `Compat` facade, not to widen the allow
list — the allow list is for genuinely shared symbols only.
