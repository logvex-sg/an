# Dependency Audit

This document records what LOGVEX CRYSTAL links, why, and what the supply-chain posture is. The
machine-readable version is `docs/SBOM.md`, generated by `build-system/generate_sbom.py` and checked
by `./gradlew checkSbom`.

## What the client links

| Dependency | Version source | Role | Licence |
| --- | --- | --- | --- |
| Minecraft (`com.mojang:minecraft`) | `build-system/versions.json` | provided at runtime | Mojang EULA, not redistributed |
| Fabric Loader | `build-system/versions.json` | provided at runtime | Apache-2.0 |
| Fabric API | `build-system/versions.json` | provided at runtime | Apache-2.0 |
| Yarn mappings | `build-system/versions.json` | build only | CC0-1.0 |
| JUnit 5 | `gradle/libs.versions.toml` | test only | EPL-2.0 |
| Gson | `gradle/libs.versions.toml` | provided; test-only direct dependency | Apache-2.0 |

The shipped jar bundles **none** of these. Minecraft, Loader and Fabric API are supplied by the
player's own Fabric installation; the mappings and test tooling never reach a release. The jar
contains only LOGVEX CRYSTAL's own classes, its own resources, and the release public key.

## Why the versions live where they do

The Minecraft / mapping / Fabric-API / Java / Loom matrix is a function of the selected
`-PmcVersion`, so it cannot be a static version catalog. It lives in `build-system/versions.json`,
generated from upstream metadata by `build-system/generate_inventory.py` and checked by
`./gradlew checkInventory`. The test-tooling versions are version-independent, so they live in
`gradle/libs.versions.toml`.

Both files are sources of truth for the SBOM, so the SBOM cannot disagree with what the build
resolves.

## Supply-chain posture

- **No bundled binaries.** The jar has no shaded libraries, no native code, and no model weights.
- **No dynamic dependency resolution at runtime.** The client does not download jars to extend
  itself; the only network features are the optional local-AI model download (user-initiated, from
  the upstream publisher, checksum-pinned) and the release update check (signature-verified).
- **Pinned coordinates.** Every dependency is pinned to an exact version. There are no version
  ranges and no `+` dynamic versions, so a build is reproducible from the two version files.
- **Signed releases.** Update artifacts are authenticated with Ed25519 before installation; see
  `docs/RELEASE_SIGNING.md`.
- **Reviewable rule sets.** The compatibility and adapter-leak rules are data files
  (`build-system/compatibility-manifest.json`, `build-system/adapter-guard.json`), not code, so a
  reviewer can see and diff exactly which symbols are allowed where.

## Optional components the user may add

The local-AI feature can use a GGUF runtime and model that the user installs themselves. Neither is
bundled, endorsed, or resolved by the build. They are documented, with licences and checksums, in
`docs/ai/THIRD_PARTY_NOTICES.md`.

## Keeping this current

When a dependency changes, change the version file it lives in, then regenerate the SBOM:

```bash
python3 build-system/generate_sbom.py
./gradlew checkSbom
```

`verifyAll` runs `checkSbom`, so a stale SBOM fails the release gate rather than shipping.
