## 1. Repository shape

- Single Gradle project (`logvex-crystal`), no sub-modules. `settings.gradle` declares one root project.
- **390** main Java sources, **96** test sources.
- `build.gradle` is inventory-driven (Phase 9). The target Minecraft version is chosen in the
  `buildscript {}` block from `build-system/versions.json` via `-PmcVersion=<x>`; default is
  `inventory.primary`.
- Two build-time compat mechanisms already exist:
  1. **Compat bands** — `compat/Compat.java` (facade) + `src/versioned/<band>/java/.../CompatHooks.java`
     (one implementation compiled per band: `pre-matrix`, `pre-world`, `no-world-event`, `pre-layers`, `modern`).
  2. **Breaking-change register** — `build-system/breaking-changes.json` → `compatibility-manifest.json`.

## 2. Compatibility reality (measured, not assumed)

Compiled each band endpoint in this audit:

```
-PmcVersion=1.21.1   FAILED  (assets/AssetRegistry, gui/ClickGui: cannot find symbol)
-PmcVersion=1.21.5   FAILED
-PmcVersion=1.21.6   FAILED
-PmcVersion=1.21.8   FAILED
-PmcVersion=1.21.9   BUILD SUCCESSFUL
-PmcVersion=1.21.10  BUILD SUCCESSFUL
-PmcVersion=1.21.11  BUILD SUCCESSFUL (from cache)
-PmcVersion=26.3     FAILED  (100 errors; "package net.minecraft.text does not exist")
```

The `compatibility-manifest.json` `summary` corroborates this and names the outstanding work:

```json
{ "totalVersions": 16, "versionsNeedingShims": 10,
  "versionsNeedingNamespaceMigration": 5,
  "versionsWithPendingWork": ["1.21.1","1.21.2","1.21.3","1.21.4","1.21.5",
                              "1.21.6","1.21.7","1.21.8"] }
```

The eight `pendingChanges` per affected version are: `render-pipelines`, `input-records`,
`entity-pos`, `fabric-resource-events`, `entity-render-state`, `misc-api-renames`
(plus, for 1.21.9, `fabric-world-events` is absent by design).

**Conclusion:** the honest, supported range today is **1.21.9, 1.21.10, 1.21.11**.
Everything else in the intended `1.21.1 .. 26.3` range is either **experimental/blocked**
and must be reported as such. This audit explicitly refuses to advertise 1.21.1–1.21.8 or
26.x as supported "because metadata allows it to load".

## 3. What the spec assumes but does not exist

The Phase 11 brief says *"build upon the existing … Overseer controller, configuration
system, and updater"*. Ground truth:

- **Overseer controller: does not exist.** The remote subsystem it would build on does exist
  and is good, but there is no edition, no controller UI, no fleet workspace.
- **Updater: does not exist.** Must be built from scratch.
- **Overseer fleet / release dashboard: does not exist.**

An earlier attempt in this same session to invent an "Overseer" build variant was reverted
(it was unrequested then); Phase 11 *does* request it, so it will be built properly now, on
top of the verified `remote/` subsystem.

## 4. Critical problems to fix before building on top

1. **No adapter-leak guard.** Shared modules can import version-specific classes freely; the
   spec requires an automated check. → Build a guard script + a JUnit test + a Gradle task.
2. **Editions are not separated.** There is a single artifact today. The spec forbids
   "renaming the same JAR"; the two editions must differ in an actual build input
   (a feature manifest resource). → Real separation, see §5.
3. **No machine-readable version registry.** `versions.json` records metadata but no
   `supportStatus`/`buildStatus`/`testStatus`/`releaseStatus`. → Extend the registry.
4. **No artifact validation / metadata / manifests / signatures.** → Build the release factory.
5. **26.x namespace layer absent.** Cannot be fixed without a namespace facade; classified
   BLOCKED and reported, not faked.

## 5. Edition separation design (decided here, implemented in Phase 11)

The two editions are **one source tree with a build-time feature manifest**:

- `src/main/resources/logvex-features.txt` — the Standard manifest (empty: no optional features).
- `src/overseer/resources/logvex-features.txt` — the Overseer manifest (lists the Overseer feature).
- A tiny `variant/FeatureRegistry` in the shared core reads the manifest from the classpath and
  starts whatever feature classes it names. The core never references a feature class by name.
- The Overseer source set is added to the *same* main compilation for the Overseer edition
  (so it shares the core, exactly as the spec asks), but ships its own manifest resource, which
  is what makes the artifact genuinely different rather than a renamed copy.

This keeps the editions separate, keeps the core free of admin code, and needs no reflection.
